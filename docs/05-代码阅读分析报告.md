## 1. 一句话结论

这是一个 **“Windows 本机监控服务 + ASP.NET Core Web API + SignalR + SQLite + Vue3 前端”** 的多项目解决方案，目标是：

- 在 Windows 机器上持续采集 **硬件信息**
- 通过 ETW 采集 **网络流量**
- 把历史数据写入 **SQLite**
- 通过 **HTTP API + SignalR** 提供给前端页面
- 最终以 **Windows 服务** 形式部署

整体设计思路是对的，模块拆分也比较清晰，但当前仓库处于 **“主体框架已搭好、关键功能大部分已写、但还没彻底收口”** 的状态。

## 2. 项目整体结构

解决方案文件：`win11-system-monitor.sln`

包含 6 个后端项目 + 1 个前端目录：

- `Monitor.Service`：宿主进程，程序入口
- `Monitor.Hardware`：硬件采集
- `Monitor.Network`：网络采集与聚合
- `Monitor.Storage`：SQLite 存储
- `Monitor.Contracts`：DTO/配置/公共枚举
- `Monitor.WebApi`：API、SignalR、异常处理中间件
- `Monitor.Frontend`：Vue3 + TypeScript 前端

### 分层关系

可以把它理解成这条链路：

```text
Windows 传感器 / ETW
        ↓
采集层（Hardware / Network）
        ↓
聚合/缓存层（Buffer / Aggregator）
        ↓
持久化层（Storage / SQLite）
        ↓
服务层（WebApi / SignalR）
        ↓
展示层（Vue Frontend）
```

这个分层很标准，优点是：

- 采集逻辑和 API 逻辑解耦
- 存储逻辑集中
- 前端只依赖 contracts 对应的数据结构
- 后续补测试也容易按模块拆

## 3. 启动流程：程序是怎么跑起来的

入口文件：`src/Monitor.Service/Program.cs`

### 启动顺序

1. 尝试处理命令行安装/卸载服务（但对应实现缺失）
2. 创建 `WebApplicationBuilder`
3. 读取 `appsettings.json`
4. 再从 SQLite 的 `settings` 表读取持久化配置，并叠加到配置系统
5. 启用 Windows Service 托管
6. 配置 Serilog 日志
7. 注册各模块依赖注入
8. 注册后台任务：
   - `CollectorHostedService`
   - `AggregationHostedService`
   - `CleanupHostedService`
   - `DatabaseInitializationHostedService`（在 Storage 中注册）
   - `MonitorRealtimePushHostedService`（在 WebApi 中注册）
9. 创建应用
10. 根据配置绑定监听端口
11. 注册 API / Hub / 中间件 / 静态文件
12. 运行

### 这个设计的关键点

它不是传统“控制台程序 + 单独 Web 服务”，而是：

> **一个 ASP.NET Core 宿主，同时承载 Web API、SignalR、后台采集任务、数据库初始化任务。**

这在 .NET 里很常见，也很适合这种“本地服务程序”。

## 4. 每个项目在做什么

## 4.1 Monitor.Contracts

这是整个系统的 **公共契约层**。

它包含：

- DTO：前后端交互的数据格式
- 枚举：协议、方向、地址范围
- Options：配置对象

### 你要这样理解它

它不是“业务逻辑层”，而是“协议层”。

比如：

- `HardwareRealtimeDto`：给前端看的硬件实时数据
- `NetworkRealtimeDto`：给前端看的网络实时数据
- `AppSettingsDto`：设置页用的配置 DTO
- `MonitorSettings`：后端配置绑定对象

### 重要设计点

`MonitorSettings` 用了数据注解做校验：

- `[Range]`
- `[Required]`
- `IValidatableObject`

这是 .NET 配置系统里非常典型的写法：

- 配置先绑定到类
- 启动时自动验证
- 非法配置直接拒绝启动

### 当前问题

`HardwareRealtimeDto` 引用了两个缺失类型：

- `DiskTemperatureDto`
- `DiskSpaceDto`

前端 TypeScript 里有对应定义，但后端 C# 没补上。

## 4.2 Monitor.Hardware

这是 **硬件采集模块**。

### 主要职责

- 封装 LibreHardwareMonitor
- 读取 CPU、内存、存储传感器
- 生成统一的 `HardwareSnapshot`
- 提供磁盘占用信息

### 核心类

- `IHardwareCollector`
- `LibreHardwareCollector`
- `IHardwareSnapshotBuffer`
- `HardwareSnapshotBuffer`
- 一组模型类：`CpuMetrics`、`MemoryMetrics`、`DiskMetrics`、`SystemMetrics`

### 真正的核心：LibreHardwareCollector

这个类非常大（999 行），本质干了两件事：

#### 第一部分：调用 LibreHardwareMonitor 拿传感器数据

它会：

- 打开 `Computer`
- 开启 CPU / Memory / Storage 传感器
- 遍历硬件树
- 找出：
  - CPU 占用
  - CPU 温度
  - CPU 频率
  - CPU 功耗
  - Memory Used / Available
  - 磁盘温度

这个类里有很多“兜底逻辑”，例如：

- CPU 温度优先找 `CPU Package`
- 如果没有，再找 `Core Max`
- CPU 频率优先读 `Clock`
- 没有再读 `Frequency`

这说明作者已经考虑到了 **不同机器传感器名字不完全一致** 的现实问题。

#### 第二部分：通过 Win32 API 推断“传感器里的磁盘”对应哪个物理盘/卷

这是这个仓库最复杂的部分之一。

它使用了大量 P/Invoke：

- `FindFirstVolume`
- `FindNextVolume`
- `DeviceIoControl`
- `GetDiskFreeSpaceEx`
- `GetVolumePathNamesForVolumeName`

目标是：

1. 枚举卷
2. 找卷对应的磁盘号
3. 把 LibreHardwareMonitor 里的磁盘名字和 Windows 的物理盘号映射起来
4. 再计算磁盘容量、已用空间、剩余空间

### 这个模块的优点

- 采集逻辑被封装得比较集中
- 对传感器名称差异做了兜底
- 有并发保护（`lock`）
- 有缓存最近快照 / 待持久化快照

### 这个模块的缺点/风险

1. **类太大**
   - `LibreHardwareCollector` 已经接近“上帝类”
   - 传感器采样、磁盘拓扑解析、P/Invoke 都写在一起

2. **存在缺失类型**
   - `IDiskUsageProvider`
   - `DiskDriveMetrics`
   - `DiskSpaceInfo`

3. **存在遗留未使用代码**
   - `IoctlDiskGetLengthInfo`
   - `IoctlStorageQueryProperty`
   - `ReadAnsiString`
   - 若干 Win32 结构体

说明这块经历过迭代，可能有重构没收尾。

## 4.3 Monitor.Network

这是 **网络采集与聚合模块**。

它的设计是本项目里第二个最重要的部分。

### 子模块职责

- `EtwNetworkCollector`：从 ETW 读 TCP/UDP 事件
- `ProcessResolver`：PID → 进程信息
- `AppRegistryService`：维护 app_key → 应用元数据
- `AddressClassifier`：判断 WAN/LAN/Loopback/Other
- `TrafficAggregator`：把原始网络事件转成实时视图和历史桶

---

### 4.3.1 EtwNetworkCollector

这是原始事件入口。

#### 它做什么

- 创建 ETW Session
- 打开 Kernel NetworkTCPIP provider
- 监听：
  - TCP send/recv
  - TCP IPv6 send/recv
  - UDP send/recv
  - UDP IPv6 send/recv
- 把 ETW 事件转换成统一的 `NetworkTraceEvent`

#### 优点

- TCP/UDP、IPv4/IPv6 都覆盖了
- 会自动清理残留的旧 ETW Session
- 对权限不足、资源不足做了异常处理

#### 重要现实约束

启动 ETW kernel session 往往需要高权限。  
所以这个模块在普通用户直接运行时，网络采集可能失败。

代码里也明确处理了：

- `UnauthorizedAccessException`
- ETW 资源不足（`0x800705AA`）

#### 一个很重要的设计选择

如果 ETW 启动失败，它会：

- 记日志
- **但不会让整个服务崩掉**

这意味着系统会退化成：

> 硬件监控还能跑，网络监控不可用。

这是一种典型的“降级运行”思路。

---

### 4.3.2 ProcessResolver

作用：把 PID 转成更稳定的应用身份。

#### 它返回什么

- ProcessName
- ExecutablePath
- DisplayName
- AppKey

#### AppKey 的生成方式

如果拿得到 exe 路径，就对标准化后的路径做 SHA256。  
拿不到路径，就退化成对 `processName` 做哈希。

这非常合理，因为：

- 同名进程可能来自不同路径
- 只用 PID 不稳定
- 路径 + 哈希更适合做“应用标识”

#### 缓存策略

对 PID 做 30 秒缓存，避免频繁查系统进程信息。

---

### 4.3.3 AddressClassifier

这是网络模块里设计得很不错的一块。

它会把远端地址分类成：

- `Wan`
- `Lan`
- `Loopback`
- `Other`

#### 分类规则来源

1. loopback 优先
2. multicast / broadcast / unspecified → other
3. 配置里的 `AdditionalWanCidrs`
4. 配置里的 `AdditionalLanCidrs`
5. 本机网卡子网
6. 私网 / link-local
7. 默认按公网算 WAN

#### 为什么它重要

“按 app 统计流量”不难，  
“按 app + WAN/LAN 统计”难点就在地址分类。

这个类把这块逻辑独立出来，是正确的。

#### .NET 初学者需要注意

这里用了很多现代 C# 特性：

- `record struct`
- 模式匹配
- `is >= 16 and <= 31`
- 集合表达式 `[]`

---

### 4.3.4 TrafficAggregator

这个类是网络模块真正的“业务核心”。

#### 输入

- 来自 ETW collector 的很多条 `NetworkTraceEvent`

#### 输出

1. **实时视图**
   - 当前总上传/下载速率
   - WAN/LAN 速率
   - 每个 app 的实时速率

2. **历史桶**
   - 以 `AggregateIntervalSeconds` 为粒度
   - 按 app / direction / scope 聚合
   - 写入 SQLite

#### 核心思路

- `_recentEvents`：保留短时间实时事件
- `_activeBuckets`：当前还没完成的聚合桶
- `_pendingBuckets`：已经完成、等待入库的桶

#### 工作方式

网络事件来时：

1. 根据 PID 查 app
2. 分类地址 scope
3. 放入实时队列
4. 累加到当前桶

定时触发聚合时：

1. rotate 已完成的桶
2. 生成实时 snapshot
3. 取出待持久化桶，交给 repository

#### 这个类的优点

- 内存实时视图和历史持久化分开
- 锁保护清晰
- 实时与历史都从同一份原始事件演化出来

#### 一个现实问题

它计算实时速率的方法，是取最近一个采样窗口内的事件总量，再除以窗口长度。  
这不是问题，但你要理解它代表的是：

> “最近一个窗口的平均速率”

而不是每个网卡驱动层真正意义上的瞬时速率。

## 4.4 Monitor.Storage

这是 **SQLite 持久化层**。

### 包含的内容

- 连接工厂
- 数据库初始化
- 设置读取/写入
- 硬件样本入库
- 网络桶入库
- 数据清理

### 核心类

- `SqliteDbConnectionFactory`
- `DatabaseInitializer`
- `HardwareRepository`
- `NetworkTrafficRepository`
- `SettingsRepository`
- `RetentionService`
- `PersistedSettingsLoader`

---

### 4.4.1 DatabaseInitializer

负责：

- 开启 SQLite PRAGMA
  - `journal_mode = WAL`
  - `synchronous = NORMAL`
  - `foreign_keys = ON`
- 建表
- 初始化默认 settings

这说明作者已经考虑到了 SQLite 作为长期运行服务数据库时的基本实践。

### 4.4.2 HardwareRepository

负责把 `HardwareSnapshot` 批量写到 `hardware_samples`。

特点：

- 批量事务写入
- 查询时再映射回 `HardwareSnapshot`

### 4.4.3 NetworkTrafficRepository

这是存储层最重的类。

职责：

- upsert `app_registry`
- 把 `TrafficBucket` 批量写入 `network_usage_agg`
- 查询区间桶
- 查询 app 汇总排行

这里用了 SQLite 很典型的写法：

- `ON CONFLICT ... DO UPDATE`
- `SUM(CASE WHEN ... THEN ... END)`

也就是说，这层本质是：

> “一个轻量 SQL 聚合层”

### 4.4.4 SettingsRepository

负责读写 `settings` 表。

### 4.4.5 RetentionService

负责清理过期历史数据，并在有删除时执行：

- `wal_checkpoint(TRUNCATE)`
- `VACUUM`

这个设计是对的，因为 SQLite 长期写入后如果不做空间回收，文件可能一直膨胀。

## 4.5 Monitor.WebApi

这是 **对外服务层**。

### 技术风格

它没有用 Controller，而是用了 **Minimal API**。

包括：

- `/api/overview`
- `/api/hardware/realtime`
- `/api/hardware/history`
- `/api/network/realtime`
- `/api/network/apps`
- `/api/settings`
- `POST /api/settings`
- `/health`
- `/hubs/monitor`

### 主要组成

- Endpoints
- SignalR Hub
- SignalR 推送后台任务
- 全局异常中间件
- WebApplication 扩展

### 这个模块的优点

- 路由清晰
- DTO 转换集中
- 中间件结构简单
- 适合这种轻量服务

### 当前实现上的缺口

虽然定义了 SignalR 事件：

- `hardwareRealtime`
- `networkRealtime`
- `topAppsRealtime`

但目前真正广播的只有：

- `hardwareRealtime`

`networkRealtime` 和 `topAppsRealtime` 只定义了名字，没有实际发送逻辑。

这意味着：

- 前端实时连接层支持三种流
- 后端实际上只推了硬件

所以现在的“实时能力”是 **半完成状态**。

## 4.6 Monitor.Service

这是整个应用的 **宿主层 / 编排层**。

### 它不做具体业务

它主要负责：

- 组合各模块
- 启动后台任务
- 配置日志
- 绑定端口
- Windows Service 化

### 三个核心 HostedService

#### CollectorHostedService

做的事：

- 启动网络采集
- 周期性采硬件
- 快照放进内存缓冲
- 达到阈值后批量写库

#### AggregationHostedService

做的事：

- 周期性让 `TrafficAggregator` 生成实时快照
- 把已完成网络桶批量写库

#### CleanupHostedService

做的事：

- 定期清理过期历史

### 这个项目的本质

你可以把 `Monitor.Service` 理解为：

> **调度中心 + 组合根（Composition Root）**

在 .NET 里，这种“所有依赖注入都从 Program/Bootstrapper 汇总注册”的地方，通常就叫组合根。

## 6. 我实际发现的问题清单

## 6.1 会直接导致后端编译失败的问题

`dotnet build` 报错里明确缺失：

- `DiskTemperatureDto`
- `DiskSpaceDto`

- `StoragePathHelper`
- `WindowsServiceCommandHandler`

### 这意味着什么

这不是“代码有 bug”，而是：

> **仓库里少了一批文件，或者重构时忘了提交。**

尤其是：

- 安装/卸载脚本依赖 `Monitor.Service.exe install/uninstall`
- 但 `WindowsServiceCommandHandler` 根本不存在

所以部署脚本当前也不可能真正打通。

---

## 6.2 配置保存后不会实时生效

这是一个很关键的逻辑问题。

### 当前流程

程序启动时：

1. 读 `appsettings.json`
2. 再从 SQLite `settings` 表读取持久化设置
3. 通过 `AddInMemoryCollection` 覆盖配置
4. `MonitorSettings` 绑定到配置系统

但设置页保存时：

- 只把新值写回 SQLite
- **并没有更新当前运行中的 `IConfiguration`**

所以：

- `IOptionsMonitor<MonitorSettings>` 的 `CurrentValue` 实际不会变化
- 后台任务的定时器也不会更新

### 实际效果

前端页面上“保存成功”了，数据库里也确实保存了，  
但当前进程里的运行参数不会立即变。

严格说：

> **这些设置基本都是“下次启动生效”。**

而不是页面文案里说的“部分立即生效”。

---

## 6.3 SignalR 实时能力只完成了一半

当前后端只广播：

- 硬件实时数据

没有广播：

- 网络实时数据
- Top Apps 实时排行

所以现在 Dashboard 的行为是：

- 首次请求 `GET /api/overview` 时拿到硬件 + 网络 + topApps
- 后续只更新硬件
- 网络和 topApps 会停留在初次加载时的数据

这属于典型的：

> 前后端接口和实时框架已经预留好，但联调还没做完

## 7. 这个项目里最重要的 .NET 知识点

下面这部分是给 **没系统学过 .NET** 的你准备的。

---

## 7.1 解决方案（`.sln`）和项目（`.csproj`）

在 .NET 里：

- `.sln`：解决方案，相当于“工程总目录”
- `.csproj`：单个项目配置文件

你可以把它类比成：

- `.sln` = 一个大仓库的工作区
- `.csproj` = 某个模块自己的构建配置

这个仓库是典型的 **多项目解决方案**。

---

## 7.2 `Directory.Build.props`

这是一个非常典型的 .NET 仓库级配置文件。

它会自动作用于子项目。

这里定义了：

- `TargetFramework = net8.0`
- `Nullable = enable`
- `ImplicitUsings = enable`
- `LangVersion = latest`
- `RollForward = LatestMajor`

### 这些是什么意思

#### `net8.0`

目标运行时是 .NET 8。

#### `Nullable = enable`

开启“可空引用类型”。

意思是：

- `string` 默认不该是 null
- `string?` 才表示允许为 null

这是现代 C# 非常重要的类型安全机制。

#### `ImplicitUsings = enable`

编译器自动帮你引入一批常用 namespace。  
所以很多文件里你看不到 `using System;` 之类的代码。

#### `LangVersion = latest`

启用最新 C# 语法。

这也是为什么你会看到很多现代语法。

#### `RollForward = LatestMajor`

如果机器上没有完全匹配的运行时，允许向更高 major 版本滚动。  
这是部署相关设置。

---

## 7.3 中央包版本管理：`Directory.Packages.props`

这个仓库用了：

```xml
<ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
```

意思是：

- 各项目 `csproj` 里只写 `PackageReference Include="xxx"`
- 不写版本号
- 统一在 `Directory.Packages.props` 里定义版本

优点：

- 版本集中管理
- 升级依赖方便
- 多项目不容易版本漂移

这是 .NET 多项目仓库里的推荐实践之一。

---

## 7.4 依赖注入（DI）

你会看到很多这种代码：

```csharp
services.AddSingleton<IHardwareCollector, LibreHardwareCollector>();
services.AddHostedService<CollectorHostedService>();
```

这就是 .NET 自带 DI 容器。

### 你要怎么理解

程序不是自己 `new` 所有对象，而是：

1. 先把“接口 → 实现”注册进容器
2. 用的时候由框架自动创建并注入

### 常见生命周期

#### `AddSingleton`

整个进程只创建一个实例。

适合：

- 配置提供器
- 聚合器
- 缓冲区
- 仓储

#### `AddHostedService`

表示这是后台任务，会跟着 Host 一起启动/停止。

## 7.5 Options 模式

这段代码：

```csharp
services
    .AddOptions<MonitorSettings>()
    .Bind(configuration.GetSection(MonitorSettings.SectionName))
    .ValidateDataAnnotations()
    .ValidateOnStart();
```

就是 .NET 标准的 **Options Pattern**。

### 作用

把配置文件里的：

```json
"Monitor": { ... }
```

绑定到：

```csharp
MonitorSettings
```

然后其他类通过：

```csharp
IOptionsMonitor<MonitorSettings>
```

来读取当前配置。

### 这比自己手写读取配置更好

因为它有：

- 类型安全
- 校验
- IDE 提示
- 统一管理

## 7.6 Hosted Service / BackgroundService

像：

- `CollectorHostedService`
- `AggregationHostedService`
- `CleanupHostedService`
- `MonitorRealtimePushHostedService`

这些都属于后台服务。

### `BackgroundService`

本质就是一个“长期运行的异步循环任务”。

典型写法：

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    using var timer = new PeriodicTimer(...);
    while (!stoppingToken.IsCancellationRequested &&
           await timer.WaitForNextTickAsync(stoppingToken))
    {
        ...
    }
}
```

这在 .NET 里是非常标准的“定时后台任务”写法。

## 7.7 Minimal API

你看到很多这种写法：

```csharp
app.MapGet("/api/overview", (...) => { ... });
```

这就是 ASP.NET Core 的 Minimal API。

### 和传统 Controller 的区别

传统写法：

- Controller 类
- Action 方法
- 一堆 attribute

Minimal API：

- 直接在启动配置里写路由
- 更适合小中型服务
- 更轻量

这个项目选 Minimal API 是合理的。

## 7.8 SignalR

SignalR 是 .NET 官方实时通信方案。

### 你可以把它理解成

> ASP.NET Core 官方版 WebSocket/实时推送封装

这里的用法是：

- 后端定义 `MonitorHub`
- 前端用 `@microsoft/signalr` 连接 `/hubs/monitor`
- 后端 `hubContext.Clients.All.SendAsync(...)`
- 前端 `connection.on('hardwareRealtime', ...)`

这是典型的实时大盘方案。

## 7.12 主构造函数风格

比如：

```csharp
public sealed class AppConfigurationProvider(IOptionsMonitor<MonitorSettings> settings)
```

这是一种现代 C# 写法，等价于：

```csharp
public sealed class AppConfigurationProvider : IAppConfigurationProvider
```

这叫 **primary constructor 风格**（C# 12 扩展后的常见写法）。

## 8. 代码风格与规范解读

这个仓库的 C# 风格整体偏现代，核心特征是：

- `sealed class` 很多
- 接口驱动
- DTO / Model 多用不可变初始化风格
- 依赖注入而不是手动 new
- 很少写静态工具大杂烩
- 业务逻辑按模块拆分

### 为什么很多类是 `sealed`

`sealed` 表示不希望被继承。

好处：

- 语义更明确
- 降低扩展面
- 对这种业务类通常更安全

### 为什么大量使用接口

例如：

- `IHardwareCollector`
- `INetworkCollector`
- `IAddressClassifier`
- `IProcessResolver`
- `IDbConnectionFactory`

这是典型的“面向接口编程”，方便：

- 测试替身
- 模块解耦
- 替换实现

### 为什么 DTO / Model 大多只定义属性，不写方法

因为它们的职责只是“承载数据”，不是“执行业务”。
